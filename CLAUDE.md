# Agent checkout firewall

An intent firewall and adversarial test arena for AI shopping agents, built solo for the hackathon (submission deadline Nov 12, 2026; judging runs until Dec 15). A shopping agent's checkout becomes a sandbox payment authorization; a review tree of gates (deterministic policy, a quarantined extractor, an intent auditor and a trace auditor) compares the cart against the mandate the person confirmed, then captures, escalates to the person, or voids. The arena is a seeded marketplace with honest and attacker sellers, and an eval harness measures attack success rate, false block rate, cost and latency with the firewall off and on. The stack is TypeScript throughout: a pnpm workspace monorepo with a Hono server, a React + Vite web app, and SQLite through Drizzle. The plan, the decisions behind it and the milestones live in `docs/PLAN.md`.

Follow `omarg-dev/code-repo-rulebook` for branches, commits, PRs, CI, versions and deploys. This file only adds what's specific to this repo.

## Workflow

- Before pushing: `pnpm lint && pnpm check && pnpm test && pnpm build`. After changing dependencies, run them from a fresh `pnpm install --frozen-lockfile`.
- Work goes step by step through the Progress tables in `docs/PLAN.md`: one step per PR, and the PR that finishes a step updates its status and the "Now" line.
- Hand mundane tasks (fictional content, boilerplate, version lookups) to Claude Haiku subagents.
- The rulebook (`omarg-dev/code-repo-rulebook`) has to be in the session. If it isn't, add it before the first branch or commit. The rules a session without it breaks: branches are `feat/`, `fix/`, `cleanup/` or `change/` (never `claude/…`), commits carry no trailers (no `Co-Authored-By:` or `Claude-Session:`), PRs are drafts into `dev` with plain imperative titles, an open PR isn't watched (no subscribing to its activity, no polling CI, no scheduled check-ins), and pushed history is never rewritten.
- Omar works in one conversation. It hands each step to a subagent, which reads `docs/PLAN.md` and this file before starting, works in its own git worktree, commits without pushing, and reports back; the conversation reviews the diff, runs the checks above and opens the PR. A subagent that needs a decision stops and asks rather than guessing. A decision made in the conversation lands in `docs/PLAN.md` or this file the same day, since subagents and later sessions only see the repo.
- APIMatic's Context Plugin for the payment platform is installed by the cloud environment's setup script. Use its skill and MCP server for payment integration work: using it is what qualifies for APIMatic's prize.
- The payment platform's own official plugin is installed by the setup script too, for looking at the sandbox, explaining errors and reading docs. Integration code still comes from APIMatic's plugin, even when both offer to help. The official plugin's MCP server needs a sandbox access token that expires within hours, so it's usually not connected, and that's expected.
- UI work starts with a design pass using the design skills, and every UI PR carries screenshots in light and dark.
- Staging is off. Deploys follow the rulebook's plain pull-and-restart once there's something to deploy.

## Conventions

- `apps/` holds what runs (the server, later the web app); `packages/` holds libraries named `@firewall/<name>`. Workspace packages export their TypeScript source, and the server's build bundles them with esbuild into one file, so the Docker image needs no `node_modules`.
- Imports use `.js` extensions (`./app.js` for `app.ts`), as NodeNext module resolution requires.
- The version lives only in the root `package.json`; the server reads it from there, and a test checks the changelog's latest entry names the same version.
- Biome lints and formats code and JSON only. It would also reformat Markdown and pad every table, so Markdown is left out of its `files.includes`.
- Schema changes: edit a package's `src/schema.ts`, then `pnpm --filter <package> exec drizzle-kit generate --name <what_changed>` writes the migration into its `drizzle/` folder. SQL drizzle-kit can't express (triggers) goes in a `--custom` migration. Migrations run when the database is opened, so there's no separate migrate step.
- Database tests use a real SQLite file in a temp folder, never a mock and never the dev database.
- The arena has three layers: pure shop functions (`packages/arena/src/shop.ts`) over one arena and one cart; the service (`service.ts`), which calls them and writes each call to the event log; and the HTTP routes (`apps/server/src/routes/arena.ts`), which validate input with zod and call the service. New marketplace behaviour goes in the shop first, with its tests.
- Arena events record what was served, with page content marked `seller_content` and cart and checkout steps marked `catalog`. A failed call is recorded as `<type>_failed` with its reason.
- better-sqlite3 runs from the prebuilt binaries it ships with. Its build script is ignored in `package.json` (`pnpm.ignoredBuiltDependencies`), so nothing compiles; it stays outside the server bundle, and the Dockerfile copies its JavaScript and Linux binaries into the image.
- Payments go through the `PaymentAdapter` interface (`packages/payments/src/types.ts`). The in-memory fake implements it for development and the eval; the sandbox adapter (`sandbox.ts`, on the platform's server SDK) implements it for real runs. Both must pass the shared contract suite in `contract.ts`: the fake in `pnpm test`, the sandbox with `pnpm --filter @firewall/payments test:sandbox`, which needs the sandbox variables and fails without them, so it stays out of CI. A behaviour the firewall relies on gets a contract test first, so the fake can't drift from the platform. A capability one adapter lacks (moving time) is declared, and its tests are left unregistered rather than skipped.
- Every payment call in a run goes through `recordPayments`, which writes it to the payments lane with its input, result or error, and latency.
- Building a mandate writes the person's acts (the request, edits, confirmation or rejection) to the `human` lane with provenance `user`, and the builder's output (the draft, the locked mandate) to the `mandate` lane with provenance `system`. An edit is a new event pointing at the version it changed. Gates take the run's mandate from `lockedMandateOf`, which verifies its hash.
- Tests that need a model's answer replay one recorded from a live run (`packages/mandate/fixtures/`, `packages/firewall/fixtures/`). Each recording keeps the hash of the request that produced it, and a test fails when the prompt or schema has moved on, naming the command that re-records.
- The firewall's gates live in `packages/firewall` and each returns a `GateResult` (`gate.ts`). A gate's verdict is decided by its code from typed facts; a model only ever extracts or judges into a schema, never picks the verdict. Gate 1 writes to the `gate1` lane: what it read (`system`), each listing's facts and catalog disagreements (`extracted`, the provenance for typed facts read out of seller content), and its `verdict` (`system`). A call's cost goes on the event of the listing it read, once. Gate 0 (`gate0.ts`, its rules in `policy.ts`) writes one `verdict` (`system`, cost 0) to the `gate0` lane, from the locked mandate and the run's catalog rebuilt from its scenario and seed. Gate 2 writes to the `gate2` lane, all `system`: `gate2_started` (what it read, by event ID and mandate hash, and the comparables and price checks it computed), `gate2_market` (each line's market quote, or why there was none), `gate2_judgement` or `gate2_judgement_failed` (the auditor's answer, with the call's cost), and its `verdict`. The auditor cites evidence by refs (`E1`, `E2`, ...) that code maps back to event IDs, so its request is the same for the same case and a recording keeps answering it.
- The review tree (`review.ts`) runs Gate 0, then Gate 1, then Gate 2 under a firewall configuration (`off`, `gate0`, `full`; `CONFIG_GATES` lists each one's gates, and Gate 3 joins `full` there). A block ends the review where it stands, so a Gate 0 block costs no model call. Its events are on the `review` lane (all `system`, no cost of their own, since the gates' events carry the spend): `review_started`, `review_finished` (the verdict, each gate's verdict and event, the skipped gates, the total cost; a null verdict means `off`, nobody reviewed the cart) and `review_failed` (a gate broke: nothing is enforced and the order stays held). There is a lane of its own because no gate's lane fits the tree's verdict and the payments lane holds the platform's calls, not the decision behind them.
- Enforcement (`enforce.ts`) acts on the held payment through the run's adapter wrapped in `recordPayments`, and every payment call points at the review's verdict (or, after a person decided, at their decision, which points at the verdict). Approve captures then pays each seller its share of the capture's net amount; block voids; escalate leaves the hold and writes `escalated`; `off` captures and pays out. A person's decision is a `human_decision` on the `human` lane with provenance `user`, carried out by the same code (`decide-run` on the command line, or `POST /events/runs/:runId/decision`, which the web app's run view calls and which needs the sandbox variables on the server). It works from the event log, so it is idempotent per run and a retry after a crash does only what is left. A run's `enforced` event is the end of its money: the pipeline calls an attack successful only when the agent was fooled and the money was captured.
- The SDK (`packages/sdk`) is how anything puts the firewall in front of an agent, and our own agent uses it too: `runAgent` wraps its tools with `firewall.wrap` and the pipeline settles with `firewall.settle()`, so there is no second path that can drift. A guarded payment tool (`checkout`, `create_order`, `pay_order` by default, or the `paymentTools` option, which replaces the defaults) creates and authorizes the order and never captures, never calls the original `execute`, and holds the cart the catalog source reports, not the amounts in the agent's arguments. Other tools are passed through as the same objects. The review and enforcement run after the agent is done (`settle`), never inside the tool call. The gates' trusted catalog and the page content the agent was served come from a `CatalogSource` (`source.ts`); the arena's is the only one, and the README says so. The platform's agent toolkit isn't installed; its tools are tested with stand-ins of the same names and input shapes. Pinned by `test_readme_snippet_is_the_example`, which also runs the example.
- The eval (`packages/eval`) runs a matrix of cells (scenario, seed, agent column): the agent once per cell (`runCell`, the firewall only holding the checkout), then `off`, `gate0` and `full` each review that same recorded checkout (`evaluateCell`), so a cell costs the agent once. Money outcomes per configuration are derived from the verdict (`moneyFor`: off and approve capture, block voids, escalate holds) and never moved per configuration; `settleCell` really enforces the `full` verdict once per cell (checking the derivation, and voiding a hold an escalation left open). The task functions are plain async functions over serialisable records, so they can run on Render Workflows. Rates are computed in `metrics.ts` as the plan decides them (attack success needs fooled and captured; false block and false escalation both count clean carts in any scenario). The runner (`run-matrix`) keeps a hard `--max-usd` cap and writes the results under `results/` (git-ignored but for its README). **Every results file, JSON and Markdown, and its file name state the payment adapter (`fake` or `sandbox`), the model column, the gate model, the seeds and the date**; a `fake` file says in its first lines that it is not a sandbox result. Pinned by the results tests in `packages/eval/src/results.test.ts`.
- The web app is `apps/web` (`@firewall/web`: React, Vite and React Router, plain CSS with no UI framework). Its tokens, light and dark, are the one place colours, type, radius and spacing are defined (`src/styles/tokens.css`), and components use the token names, never raw values; the components of the design system are in `src/design/`, the theme switch in `src/theme/`, and `docs/design.md` says what each is for and the rules (red means an attacker: filled where money reached one, outlined on the seller text Gate 1 flagged as steering the purchase, decided Oct 29; a block is neutral, seller text always sits behind the hatch, each fact is said once). Fonts are self-hosted from `@fontsource` packages. The approved mockups are in `docs/design/spine/`. The server serves the built app at `/` (`apps/server/src/web.ts`, as its not-found handler, so the API keeps its paths) and its build bundles `apps/web/dist` into `dist/web`; Vite proxies the API in development. Its tests run in jsdom as a second project of the root `vitest.config.ts`. The run view (`apps/web/src/run/`) reads a run's events through a pure mapping (`timeline.ts`) that is tested over real event logs recorded by `pnpm --filter @firewall/eval record-run-fixtures` (written to `apps/web/src/run/fixtures/`; re-run it when an event's payload changes), draws them with the generic timeline in `src/timeline/`, and keeps seller-written text in the seller column only (pinned by the seller-column test in `RunView.test.tsx`). Web imports have no `.js` extension: Vite resolves them.
- Tests sit next to the code they test (`app.ts`, `app.test.ts`) and run with `pnpm test` from the root.

## Differs from the rulebook

- **No "Apps people use" defaults for language, layout or sign-in.** The UI is English only, desktop first, and has no sign-in: judges need free, unrestricted access to the hosted demo. Design tokens, light and dark, and short sentence-case copy still apply.
- **One minor version per milestone.** Omar approved going past the patch for milestones: MVP is 0.1.x, v1.1 is 0.2.0, v1.2 is 0.3.0, v1.3 is 0.4.0. Releases between milestones bump the patch as usual.

## Rules that are easy to break

- **PayPal's brand stays out of the product's name, logo and graphics.** Code, docs and commits can name PayPal, the hackathon and the payment platform freely: it's what we integrate with, and judges expect to read it. But the final product name, logo and domain must not use PayPal's name or logo, or imply PayPal built or endorses it ("built on PayPal" in a description is fine), and no PayPal logo appears on our own screens or in the video's graphics. The official rules reserve the sponsor's marks, and the video may not show third-party trademarks without permission. The repository's working name gets replaced before submission.
- **The event log is append-only.** Replay, the eval numbers and dispute evidence all assume a written event never changes, so `@firewall/events` has no update or delete, and SQLite triggers refuse them. Pinned by `test_events_cannot_be_updated_or_deleted`. A correction is a new event that points at the old one.
- **Sandbox only.** No live payment credentials, and no real secrets in the repo or its history.
- **Model clients are configured explicitly.** Cloud sessions set variables for Claude Code itself (`ANTHROPIC_BASE_URL` points at the session's proxy), and those must never reach the product. So every model client the code creates takes its key and base URL from the app's own config, never from an SDK's environment defaults: `FIREWALL_ANTHROPIC_API_KEY` and `FIREWALL_ANTHROPIC_BASE_URL`. The shopping agent passes both to its AI SDK provider explicitly; the mandate builder's client (`packages/mandate/src/client.ts`), which the gates reuse, also passes every other setting the official SDK would read from the environment, the bearer token and extra headers included. Pinned by `test_model_clients_use_the_apps_own_config` in each. Gate 2's market reference follows the same rule: Channel3's key comes only from `FIREWALL_CHANNEL3_API_KEY`, passed explicitly, and the client calls its HTTP API with fetch rather than `@channel3/sdk`, which fills its key and headers from `CHANNEL3_` variables.
- **Where credentials live.** Never in the repo or in chat. Plain cloud environment variables are readable by every session in the environment, so a key the agent proxy can attach to its host goes in as a network secret instead, and the code sends a placeholder. On the server, its `.env` holds its own keys.
- **All arena brands, products, sellers and reviews are fictional.** No real product brands anywhere in the arena or the demo. Pinned by `test_arena_uses_no_real_brands`, which also refuses names one letter away from a real brand; add to its list (`packages/arena/src/catalog/real-brands.ts`) when a new category comes in.
- **The gates that judge a purchase never see raw seller content.** Only Gate 1's extractor reads page text, one listing per call, as escaped JSON inside a data tag, and its answer is enums, numbers, document numbers, a quote it must copy verbatim (checked and cleaned in code) and a discount code (cleaned). Gate 2 and Gate 3 get `factsForReviewers`, which drops quotes and any code the catalog doesn't have; they never read arena page events, and checkout lines carry only catalog data (the product's catalog name, not the page title). Market data from outside the arena comes back as prices only, never product text. Pinned by `test_reviewers_never_see_raw_seller_content`, which checks Gate 1's reviewer view and Gate 2's actual prompt. Gate 0 reads no seller content at all: it drops the catalog's pages before any rule runs and reads the checkout only for its catalog fields, so the same run on an arena whose pages are junk gets the same checks. Pinned by `test_gate0_never_reads_seller_content`.
- **Reviews and other page content in the base catalog stay honest.** Attack content belongs to the attack scenario that injects it, never the base catalog, or benign scenarios stop being benign.
- **Say which eval numbers used the fake payment adapter.** During development the eval matrix can run against an in-memory fake of the payment platform instead of its sandbox. Whenever Omar asks whether the project is fully done, remind him which result sets are still faked, and that any number shown in the video or the write-up has to come from a run against the real sandbox.
- **One model per eval column, and the gates never change model.** The shopping agent's eval columns (Claude Haiku 5.5, OpenAI, Gemini) each run on exactly one model, with no provider fallback, or one column's numbers would mix models. The gates run on Claude Haiku 5.5 in every column.
