# Design

The look is **Clasp, round two**, approved by Omar on Nov 3. It replaces Spine (Oct 28), whose rules carry over. The boards are in [design/clasp/](design/clasp/): `R2Signature` (the four carriers), `R2Type` (the display face), `R2Start` and `R2StartDark`, `R2Runs` and `R2RunsDark`, `R2Inbox`, `R2Dash` and `R2Empty`, with round one's `ClaspRun` (the run view) and `ClaspSpec` (the motion and the glyphs). They are HTML with inline styles, kept as the source of truth; they load Google Fonts and a `support.js` that isn't kept here, so they show best in the design canvas. The app self-hosts its fonts. Screenshots of the built pages, light and dark, are in [screenshots/clasp/](screenshots/clasp/).

The code is in `apps/web`: tokens in `src/styles/tokens.css`, the components in `src/design/`, the route line's styles in `src/styles/route.css`, the plain pages' and the vault's in `src/styles/page.css`, the theme in `src/theme/`, the top bar and the footer in `src/shell/`.

## The idea

Chaperone is the pause before money moves. The run page is the money's route drawn down its left side, and the one dark surface on a screen is where the money is right now. Cover the logo and the product is still itself: four carriers, none of them the mark. The route line is the run page's alone (Omar, Nov 7); every other page is a plain page of sections.

## The four carriers

1. **The route line.** A 3px aubergine spine (`--spine`) runs 68px in from the page's edge, from the title to the foot. The title is a filled station and each section a ring station joined to its heading by a short branch. `PageRoute` draws the spine and the title, and `Station` draws a section's ring and heading (`step` numbers it, `note` sits at its far end in Fragment Mono). **Only the run page (`src/run/`) uses them**, since a run really is a route with money moving along it, and a test checks that no other page has one. Every other page is `Page` and `Section` (same props, no spine, no ring): sections with a heading and no cards or dividers.
2. **One vault per screen.** `Vault` is the dark aubergine surface (`--vault`, `--vault-2`, `--vault-ink`, `--vault-muted`, `--vault-line`, with the states' inks on it as `--v-approve`, `--v-escalate`, `--v-attacker`, `--v-block`). It holds only where the money is right now, the spine passes through it turned light, and a screen has exactly one: Runs holds what is held right now ("$171.98, 2 runs waiting on you"), Start the run step, the inbox the oldest hold's cart and its two buttons (later holds sit on the page's own ground), the dashboard the full tree's column, a run's page the timeline's money column, and an empty page an empty vault (`EmptyState`). The Connect your own agent tab holds what the SDK does with a checkout.
3. **Money-state glyphs.** `MoneyGlyph` draws eight states on the bracket's geometry (24 unit grid): held, held for a person (hollow dot), captured (short bracket, a line, a dot past it), voided (the bracket shut, a bar through it), released (the shut bracket, dashed, empty), paid attacker (like captured, a larger dot), firewall off (the line and the dot, no bracket) and not reviewed (dashed bracket and a dot). They are the outcome cell, the filter chips, the place-column headers and the run view's exits, and they replace the tinted pills: `Pill` is now a glyph and a word with no tint, except **Paid attacker, which stays a filled red pill**. Each silhouette is different, so a state reads in greyscale and without its label. `moneyStateOf(run)` maps a run's outcome to one.
4. **Amounts.** `Amount` is Besley 800 with tabular figures and the fraction at half size raised to the cap line (`$109` and a small `.99`); `Rate` sets 68.8% as 68 and a raised `.8%`. **An amount is written once, in its place column**: the Runs grid has Held, Moved and Voided, and `placeOf(run)` (`runs/money.ts`, pure) says which one a run's money is in, from the money and not the verdict (an open hold is held; paid out is moved; a closed hold nobody was paid from is voided, which includes a hold released with no decision). Attacker money is red in Moved, voided money is struck through. Screen readers get the whole amount once.

## The bracket

The bracket stays where Clasp put it, and nowhere else: the mark in the top bar; the run view's big bracket around the held amount, with its dark money column (the vault); the locked mandate's **seal** (`Seal`: the bracket closed around the hash, "Locked by you, sha256 ..., date", on Start when the mandate is locked and on the run view's mandate); and the brackets round the reviewed runs' dots on the dashboard. Its corner radius is 14px (`--radius-clasp`); everything else is 2px (`--radius`).

## Motion

The clasp moment is plain CSS driven by the run's state and the replay position (`run.css`, `timeline.css`; pinned by `run/motion.test.ts`). The header's money block is keyed by its state, so a replay that crosses into a new state plays that state's motion. Block draws the bracket's right arm down in 320ms and strikes the amount through; approve slides the money out of the bracket in 500ms; escalate gives one amber ring pulse on the money's dot. All use `cubic-bezier(.2,.8,.2,1)`, none loops, and `prefers-reduced-motion` shows the end state.

## Rules

- **Red means an attacker.** `--attacker` is filled where money reached one: the amount, the Moved column, the payout path and the "Paid attacker" pill. It is outlined, never filled, on the seller text Gate 1 flagged as steering the purchase: the passages it copied, the "Fact crosses" chip and its card in the seller column. Not errors, not warnings, not a blocked cart (Omar's decision, Oct 29).
- **A block is neutral.** A block is the firewall working, so it is graphite (`--block`), not red.
- **Seller text always sits behind the hatch.** Anything a seller wrote goes in a `seller` zone, which draws the hatch and gives the text its own ground. The hatch means seller-written text and is **not a brand texture**: it appears nowhere else.
- **Each fact is said once.** A screen doesn't repeat a verdict, an amount or a reason in a second place. An amount is written once, in its place column; a summary row can open to detail, but the detail doesn't restate it.
- **A state reads without colour.** The eight glyphs have eight silhouettes.
- **Copy is short, in sentence case, with no em dashes.** Say what happened, then what is the person's to decide.
- **English only, desktop first, no sign-in.** Desktop is what is designed; a phone (390px) has to work well, not be a second design: nothing scrolls sideways outside its own frame, text is readable and controls are at least 44px tall. Below 760px the top bar folds into a menu (see The shell) and the route's offsets shrink.
- No PayPal branding in the product's name, logo or graphics.

### Type

**Besley** speaks: page titles and verdict sentences (700), money and rates (800), and what the person said, in italic (`.t-voice`). **Archivo at its normal width** works: the interface, 400 to 800. No `font-stretch` or width axis is used anywhere (the font is loaded from its weight-axis file only). **Fragment Mono** records: run IDs, hashes, times. All three are self-hosted from `@fontsource` packages, so the hosted demo needs no request to a font service.

### Theme

The theme follows the device until the person picks one. The switch is **one button between light and dark** (`ThemeSwitch`), drawn as the icon of the theme a click switches to (a moon on light, a sun on dark) and named for what it does, "Switch to dark theme". A pick is stored in this browser (`localStorage`, key `chaperone-theme`) and written to `<html data-theme>`. Switching back to the theme the device shows drops the pick, so the page follows the device again and the one button undoes itself (`toggled` in `theme.ts`): there is no third "match device" option to explain (Omar found the three icons awkward, Nov 11).

## The shell

`src/shell/` is the top bar, the page and the footer, on every page.

- **The top bar** is one row, 72px, sticky: the wordmark (home), Runs, Waiting on you with its count (the inbox, at `/escalations`; the label is what the count counts), Dashboard, Docs, then the theme button and "Start a run", the one filled button, at the far end. Where you are is a dot of the hold's colour beside the link.
- **On a phone** (760px and under) the bar is 56px: the wordmark, Start a run, and a **Menu** button. The button opens the links and the theme button as a panel under the bar (`aria-expanded`, `aria-controls`); opening it moves the focus to the first link, Escape closes it and gives the focus back, and following a link or pressing the page closes it. Closed, the panel isn't drawn, so it isn't read or tabbed to. The closed button shows the count when a purchase is waiting ("Menu, 1 purchase waiting on you"). Under 380px the button is its icon alone, and under 340px the wordmark is the mark alone.
- **The footer** (`Footer.tsx`) is on every page: "Made by Omar Ghazal" and his address as a mailto link, Docs, "Source on GitHub", "MIT licence" (the LICENSE file on GitHub), and "Built on PayPal's sandbox. Sandbox money only." Words and links only: no company's logo, there or anywhere. A page doesn't say what it is built on a second time; the home page keeps its own "Works with" line above it.

## The mark and the wordmark

The mark is the **Hold**: a rounded bracket holding a dot, "the pause before money moves". `src/design/Mark.tsx` builds it from its construction rule on a 48 unit grid (the corner radius equals the dot's width, the stroke is half the dot, the dot sits a little toward the opening, clear space is one dot), with a hand-cut version below 20px. It takes its colour from `--hold`. The wordmark is the mark and "Chaperone" in Besley 700. The product's name, logo and graphics never use PayPal's name or logo; "built on PayPal" as plain text is fine.

## Grids

Every table is AG Grid, through one wrapper and one theme, and the pages never import AG. Enterprise is on, unlicensed (its watermark shows), under the allowance the AG Grid team gave on the hackathon Discord, for the dashboard and the Runs history only, behind the `ENTERPRISE` flag in `src/grid/flag.ts`. The Runs history and the dashboard's table of every run are the two grids; a new table goes through the same wrapper.

- **One wrapper, one theme.** `src/grid/DataGrid.tsx` takes rows, columns (`GridColumn`, which is AG's column definition under our name), a label, a row ID and a few optional props (`layout`, `sort`, `onRowActivate`, `detail`); `src/grid/theme.ts` sets AG's theming parameters to `var(--token)` from `tokens.css`, so the grid follows light, dark and the theme switch with no second theme and no raw colour. `src/styles/grid.css` styles only what pages put inside it (the cell stack, the open row, the detail). It should look like the app: the headers are the sunk ground in the meta size, a row is 56px with the title in the body size and the IDs in mono, the focus ring is `--focus`, and the pinned column is told apart by a line, not a shadow.
- **Enterprise, only what is used, behind one flag.** `ENTERPRISE` off removes the Enterprise packages from the build and the controls that need them from the pages. The modules registered are the client-side row model, the column, row, scroll and row-model APIs and row styling (community, with AG's development checks in development only) and, from Enterprise, master/detail, row grouping, aggregation, cell selection, the status bar and Excel export, and integrated charts in a chunk of their own. No license key is set, so AG's watermark and a console notice show.
- **Filtering is ours.** The toolbars filter in pure functions and the grid is given the rows that pass, so the page owns the count, the empty state and the address, and none of AG's filter modules or its side bar load. A page doesn't also use AG's column filters or its quick filter: one mechanism. A toggle (`Toggle` in `src/design/`) is for how rows are shown, such as grouping, and isn't a filter.
- **Sorting is the grid's, kept where the page wants.** The Runs page passes `sort` and `onSortChange`, so the sort is in the address; the dashboard lets the grid keep its own. A column's comparator is a pure function with its own tests.
- **Long tables are drawn as they scroll, short ones whole.** `layout="scroll"` fills the window and draws only the rows in view (the history); `layout="auto"` draws every row and scrolls inside a maximum height (the 60 runs of a matrix), so a keyboard user isn't caught in a second scroll area for a short table.
- **A row can open a detail.** The `detail` prop is AG's master/detail: the detail is the row's own, so it sorts, filters and moves with it. The open row is tinted `--hold-tint` and the detail sits on `--sunk`. The control is a real button in the row's first cell with `aria-expanded`.
- **A table can be grouped.** A column marked `rowGroup` makes a group row for each value, drawn in the pinned scenario column (`showRowGroup`) with its own chevron button (`aria-expanded`), the run count and, in each aggregated column, a figure from a `sum`. Group rows sit on `--sunk`, open closed, and open and close with a click, Enter or Space. A group figure is red only when money reached an attacker.
- **Charts are drawn in the page**, in a panel under the toolbar (not a floating window), from the table's own cells: `Chart attacks` and `Chart picked cells`. Their colours are tokens (read from the page's style when the theme changes, so light, dark and the switch all work), the series are told apart by hue and are never red (red means money reached an attacker), and the chart's title is the panel's heading, said once.
- **The Runs history has a status bar** with where the money of the runs shown is, in four places (held right now, moved to sellers, paid to attackers in red, voided), worked out from the filtered runs and not read back from the grid, and "Download the evidence" in its heading.
- **Accessible.** AG's grid, row, columnheader and gridcell roles, `aria-sort` on a sorted header, rows in the page in the order they are on screen, a visible focus ring, and a keyboard path for everything a pointer can do: arrow keys between cells, Enter or Space on a row to open it, Enter on a header to sort, Tab to leave. Meaning is in text and silhouettes, not colour. It is read at 1440 wide and scrolls sideways below that, with the scenario pinned.
- **The grid is one lazy chunk.** `src/grid/index.tsx` is what a page imports and `DataGrid.tsx` is what loads, so the Runs page paints its toolbar and count at once and the grid arrives (community about 730 kB, 207 kB gzipped; the Enterprise modules about 555 kB, 155 kB gzipped, shared with the dashboard, which loads on demand too; the charts about 2.4 MB, 680 kB gzipped, loaded only by the dashboard's grid). The main bundle holds none of it. Register a module only for a feature a page uses.
- **Spine rules apply in a grid.** Red is filled only where money reached an attacker, a block is neutral, each fact is said once (a detail adds what the row doesn't say), copy is sentence case with no em dashes.

## The run view

`/runs/:runId` (`src/run/`) draws one run as the round-one `ClaspRun` board does, in Besley: the headline, the held amount in its bracket, the mandate with its seal, the decision as a station in the hold's tint, and the timeline whose money column is the vault, with the route drawn as the bracket's long arm. `timeline.ts` is the pure mapping from the run's events to a model (the outcome, the money, the items), tested over real logs; `RunTimeline.tsx` draws the model with the generic timeline in `src/timeline/`, whose items are only a time, a zone, a kind, a title and a body, so a different vertical timeline could replace it.

- **Where a finding goes is the zone it read.** Gate 0's rule results are a card in the catalog column beside its station, Gate 1's reading is a card in the seller column (with the passages it copied), and Gate 2's judgement is a card in the catalog column. The station on the spine holds only the verdict and what the gate reads.
- **The seller column is the only place seller words appear**, including the passages Gate 1 copied and the page text they are marked in. Titles, reasons and the header never quote them; the cells carry `data-zone`, and a test checks it.
- **Rows are moments, not a time scale.** Each row is an event or a group that shares one (what the agent opened and what it was served), labelled with the seconds into the run. The mockup scales rows by time; real runs have long quiet gaps that would stretch the page.
- **Filled red is given by the payee, not the config.** A run turns red when a payout went to a seller the server says is an attacker (`GET /events/runs/:runId/payees`), whatever the firewall setting was.
- **Outlined red is given by Gate 1.** The passages it copied as steering (the `marked` segments), the "Fact crosses" chip and its card get a 1.5px `--attacker` outline, as the mockup draws the poisoned review. It shows on any run where Gate 1 flagged something, whatever the verdict, since it says where an attacker's money would have come from; the page doesn't have to know whose review is poisoned, only what the extractor flagged. The outline sits on the seller text and its card, so it never reaches the header or the route. It is at least 5:1 against the seller ground in light and dark, so it needs no tint.
- **The mandate says what it didn't enforce.** The terms row "Not enforced" lists words from the request that weren't made a rule ("mid-range"), with the hint "In your request, but not made a rule".
- **The route ends in three exits**: capture and pay the seller, to the person, void the hold. The one taken is solid, the others dashed.
- **An escalated run shows the held cart and the two options** from the `R2Inbox` and round-one boards, with Reject as the filled button. They post to `POST /events/runs/:runId/decision`.
- **A page Gate 1 copied a passage from is open**, so the outlined passage is seen where it was written and not behind a closed row; the pages with nothing flagged stay closed.
- **A run in progress is read again every 1.5 seconds** until its money is settled, a gate broke, or a person has to decide.

## The Runs page

`/runs` (`src/pages/Runs.tsx`) is the history: every run, newest first, in a grid that draws the rows in view as it scrolls, so it stays quick with the few thousand an eval and a busy demo write (a history isn't paged). `src/runs/filters.ts` and `src/runs/sort.ts` are the pure side (reading and writing the filters and the sort, applying them, the order), and `src/runs/state.ts` says how a run ended. Screenshots are in `docs/screenshots/ag-grid/` and, for the Enterprise features, `docs/screenshots/ag-grid-enterprise/`.

- **Filters sit above the grid**: a search, then outcome, firewall setting, scenario and attack or benign, with "Clear filters" once any is on. Each is one native select, which is keyboard and screen-reader complete for free. The search finds a run by any part of its ID, its scenario's ID or its scenario's title. Filtering is ours and the grid is handed the rows that pass (see Grids), and the count says "66 runs", or "Showing 13 of 211 runs" once a filter is on.
- **The filters and the sort live in the address** (`?outcome=blocked&firewall=full&scenario=sc_a01&kind=attack&q=mvsq&sort=-verdict`), so a filtered, sorted view can be shared. Only what differs from everything is written (newest first is the plain address), a value that means nothing is read as no filter, and a link from before the grid (`page=2`) opens the same filters with no page. Typing in the search writes the address when the typing pauses, and "Clear filters" keeps the sort.
- **The columns sort**: a click on a header, or Enter on a focused one, sorts it, and the arrow says which way. Scenario sorts by the title it is shown under, Started by time, Firewall in the order off, Gate 0 only, full, and Verdict with what needs an eye first: money that reached an attacker, then what is waiting for a person, a broken review, a released hold, blocked, approved, firewall off and not reviewed yet. Two runs that compare equal keep the order they came in. Columns resize by dragging their edge, and the scenario is pinned left.
- **Keyboard**: a Tab into the grid lands on a header or a cell, the arrow keys move between cells, Enter or Space on a row opens its run, and Tab leaves the grid after the cell in focus instead of walking every cell of a long history. A run's title is also a link for a pointer.
- **An outcome is exactly one of eight**: approved, blocked, held for a person, hold released, paid attacker, firewall off, review failed, or not reviewed yet, in the run view's own order of precedence (money that reached an attacker first, however the run got there). The grid shows the same "Paid attacker" pill as the run view.
- **Held for a person follows the money.** An escalated run is one of four things, from whether a person decided and whether the platform's hold is still open (`escalationOf` in `@firewall/events`, which the server's run list, the web's `isHeldForPerson` and the run view's `buildRun` all use, so none can disagree): *waiting* (nobody decided, hold open), *unfinished* (a person decided, but the hold is still open or the payouts never finished), *released* (hold closed with nobody deciding) and *decided* (a person decided, hold closed). Waiting and unfinished are "held for a person": they are the filter, the top bar's count and the inbox. A released run is its own outcome, "Hold released", with no pill and no decision to make: the eval voids the hold of every escalated cell when it settles it, and those aren't waiting on anyone. An unfinished run shows the escalate pill and "Decision not finished" in the grid.
- **The firewall column says which setting the outcome comes from**, the last review's, and, small beside it, which settings reviewed the same checkout before it ("after Off, Gate 0 only"): an eval cell is reviewed under off, gate0 and full. The firewall filter is on that last setting.
- **Attack or benign comes from the arena**, not the run's name: the server answers it from the scenario (`kind`), as it answers whether an attacker was paid (`attackerPaid`, rebuilt from the scenario and seed, never guessed). The scenario cell marks an attack scenario with a small "Attack" badge, and says "Practice money" or "Sandbox" quietly when the run recorded which. This is an operator's view, like the payees.

### Runs: the money columns

The grid reads, left to right: Outcome (a glyph and a word, or the filled pill) and Scenario pinned left, Firewall, then **Held, Moved and Voided**, Started and the run's ID. A run's amount is in exactly one of the three (`placeOf`), with what it is under it ("waiting on you", "to Larkspur Goods", "voided"); a run that has had no money has none. Above the grid, the outcome is a row of glyph chips with the count each would show among the other filters (real radio buttons), and the page opens on the vault of what is held right now. The mockup's Newer and Older buttons are not built: the history scrolls and isn't paged. The grid's theme sets a 2px ink rule under the header, a 62px row, no wrapper border and a 2px radius, through AG's parameters only; the money columns are ruled off by a cell class.

## Replay

A finished run (or one waiting on a person) has "Replay this run" above its timeline; a run in progress is followed live and offered the replay once it is over. Replay plays the run's own events in log order, and the timeline builds up as the playhead passes each one. It draws `buildRun(events.slice(0, position))`, the same mapping as the live view over a prefix of the log, so it can't drift from it; at the last position it is the run view. The pure side is `src/run/playhead.ts` (positions, delays, keys, what to call an event); `useReplay.ts` holds the state; `ReplayBar.tsx` is the control.

- **The bar sits at the foot of the page and stays in view** while the timeline is read: play and pause, a step back and forward, a scrubber over the events with "12 of 45 · 6.8s", the speed (1×, 4×, Instant) and "Exit replay". Under it, one line says what the event at the playhead was ("Gate 1 flagged a passage as steering"), in fixed words: a seller's text never reaches it.
- **Speed**: 1× waits the real gap between two events, with a quiet gap capped at 1.5 seconds (a model turn can take half a minute), 4× a quarter of that, Instant goes straight to the end.
- **The position is `?at=<n>`**: how many events are shown, from 1. An event's ID works too (`?at=ev_0028`), and a position past the end is the end. It opens a shared link at that moment, paused. The address follows the playhead once it is still, and is left alone while it plays (a browser limits how often a page may rewrite its address).
- **The header follows the playhead.** The headline, the money (held, then captured or voided, and red only once a payout reaches an attacker), the cost and a "Replay, event 12 of 45" badge are those of the log up to that event. A decision that was already made isn't offered again while the playhead is before it.
- **Keyboard**: space plays and pauses, the left and right arrows step one event, Home and End go to the ends. A button keeps its own space, a slider its own arrows, and a search box or menu everything.
- **Reduced motion**: with `prefers-reduced-motion` the replay opens paused on the first event, to be played or stepped, and the page scrolls to the newest row without animating.

## Escalation inbox

`/escalations` (`src/pages/Escalations.tsx`, with `src/inbox/`; "Waiting on you" in the top bar and as its title) is every purchase held for a person: each escalated run whose hold is still open, whether nobody has decided it or a person decided and the money hasn't moved, the same rule as the count in the top bar (`isHeldForPerson`, see the Runs page). A hold released with no decision isn't listed. The oldest hold comes first, since it has waited longest. It is what the Spine-Decision mockup becomes when there are several, with the decision made from the list.

- **An item says what the run page says.** The request, the held cart, and one line for each gate that escalated come from `buildRun` (`heldReasons` is the title of that gate's card in the run view), so the inbox can't disagree with the run. It is read from the run's events once, and again only when the run has grown. A gate's line never quotes seller text, and the inbox has no seller zone.
- **How long it has been held** is the time since the review escalated ("Held for 7 hours", on hover the time itself), and **when the hold ends** is the authorization's expiry as the payments lane recorded it ("Hold ends in 28 days"). The sandbox may not report an expiry; then nothing is said, and it is never worked out. A hold already released says nothing either.
- **Deciding is the run view's call.** `useDecision` and `DecisionButtons` (`run/DecisionPanel.tsx`) are shared: Reject and release hold is the filled button, Approve and pay the secondary, and the server's own message ("This server can't carry out a decision: ...", or the platform's refusal) is shown under them. The buttons stay on screen when the server can't decide, because a fake-adapter run can't be decided from the server.
- **A decided item leaves the list** and a short note takes its place at the top: "Approved. $109.99 was captured and the seller paid." or "Rejected. The hold on $128.98 was released and nobody was paid.", with a link to the run and a way to dismiss it. A decision that was written but not carried out (the platform refused) keeps its item in the list, since its hold is still open, until it goes through: the item says "Decision not finished", which decision was recorded and why the last attempt failed, and offers one button, "Finish and pay" or "Finish and release hold", which sends the same decision again (the server finishes what is left; the opposite decision is refused with a 409). The run view's decision panel does the same.
- **A released hold has nothing to decide.** The run view says "The hold was released without a decision." with the money voided and no buttons, and a decision sent for it anyway is refused with a 409 before anything is written.
- **Recently decided** lists the last five runs a person decided and whose money has moved, with Approved or Rejected (a reject is a block, so it is the neutral pill), and how long ago. It leaves out what the page just confirmed.
- **Colour.** A held purchase is amber (`escalate`), never red: nothing has reached an attacker.
- **It stays current.** The list is read again every 7 seconds while the tab is visible, and at once when the window gets focus or the tab comes back, so a run that escalates appears without a reload. It stops when the page is left. The list isn't drawn until each held run has been read, so an item doesn't move as the rest arrive.
- **Empty**: "Nothing is waiting on you", with the same `EmptyState` as the rest.


## Dashboard

`/dashboard` ("How it's doing", `src/dashboard/`) is the `R2Dash` board with the strip of this server's runs added. It is two things that must not be mistaken for each other, so they sit apart and the first says what it is.

- **This server's runs** is a small strip at the top: runs, waiting on you, paid an attacker, blocked, approved, holds released, counted from the run log by the Runs page's own rules (`live.ts`; waiting is `isHeldForPerson`, the top bar's count). It says "Counted from the run log here, not from the eval". Each number links to the runs it counts. Red is the attacker count above zero, amber is a person waiting, and zero is neutral.
- **The eval** is one results file at a time: the newest, or an older one from the picker (`?result=<name>` keeps the choice in the address; a name the server doesn't list is the newest). `results.ts` is the pure side and takes the rates from the file as the harness wrote them (`metrics.configs`, `@firewall/eval/view`); it never counts one again.
- **Every view of a result states where it came from**: payment adapter, agent and its model, gate model, seeds, date, how many runs and what they cost, and when a spend cap stopped the matrix early. A `fake` result carries a banner, "Development numbers, not a sandbox result", in the escalate amber: not red, since nothing reached an attacker by the numbers being fake, and amber is the colour of "look at this". The picker names the adapter on every option.
- **The comparison** has a column for each setting on its own ground (Off the sunk ground, Gate 0 only the catalog ground, the full tree the vault) and a row for attack success: the number in Besley, red above zero and neutral at zero, with a dot for each attack run (red outside the bracket reached the attacker, aubergine inside it was held or blocked, grey was never fooled; a bracket means someone reviewed the cart). Under it, false blocks, false escalations, sent to a person, review cost and review time. The sentence over it ("With the full tree, no attack reached the attacker.") is said from the file's counts, and says so when some did.
- **The table of every run** is AG Grid, one row for each cell of the matrix, attacks first: scenario (pinned left), seed, kind, what the agent did, what each setting did to the money (the Runs page's pills: red "Paid attacker", neutral "Blocked", amber "Sent to a person", green "Paid seller") and a link. Columns sort, worst outcome first. "Group by attack" draws one row for each attack with how many of its runs got through under each setting (what Gate 0 only let through is one view), and "Chart attacks" and "Chart picked cells" draw a chart in a panel above the table. The filters above it are ours (kind, "Ended as" with "Under" a setting, a search), the same selects as the Runs page, so the grid only draws the rows that pass. A run links to the run view only when this server holds it: the eval's runs live in the results' own event log, so otherwise the cell says "Not on this server". An attack that succeeded without paying an attacker (the agent was fooled and the money captured, to an honest seller) says "Attack succeeded" in plain bold, since red means money reached an attacker.
- **A row opens its cell under each setting.** A click on a row (or Enter or Space on it, or the arrow at its start) opens it directly underneath, and opening another closes the first. The panel is the matrix cell read three ways: a column each for Off, Gate 0 only and the full tree, a row for each gate that ran or was skipped in any of them (the gate's verdict, how long it took and what it cost when it called a model), then the review's verdict, its cost and its time. Where the tree stopped, a gate says "Didn't run" and one line under the table says why, once ("Gate 1 and Gate 2 didn't run under Full tree. Gate 0 blocked, which ends the review."). All of it is the results file's own numbers, worded by `dashboard/detail.ts`. The row above already says what the money did, so the panel doesn't say it again: it says why. Blocks are neutral pills and nothing in it is red. A review that failed says so and has no verdict. Screenshots are in `docs/screenshots/ag-grid/` and, for the Enterprise features, `docs/screenshots/ag-grid-enterprise/`.
- **Empty**: "This server has no results folder." when `RESULTS_DIR` points nowhere, "No eval results yet." when the folder is empty, and a note naming any file in it that couldn't be read and why.


## Start a run

`/start` (`src/start/`) is where a person starts a live run, reached from the "Start a run" button in the top bar (the page's one filled action) and from the empty Runs page. Screenshots are in `docs/screenshots/onboarding/`. It has two tabs, "Run a shopper here" and "Connect your own agent" (`?tab=agent`).

- **Written for someone who isn't a developer.** A judge clicks here right after the home page. Each step says what it is, what to do and what comes next; the page says "rules" for the mandate (naming the mandate once, in step two, since the run page and the server's messages use the word), "Full check, Rules only, Off" for the firewall settings, and never shows a run ID or a config name. The seal keeps the hash, with a line saying what it is for.
- **Three steps, one sequence.** Pick a task, check the rules, start the run: three numbered sections, the done ones folded to a ticked summary line, and a hidden list that says the same to assistive technology (`aria-current="step"`). Not a wizard: nothing is hidden behind a Next, and the address keeps the draft's run (`?run=`) and the setting (`?firewall=`), so a reload picks the person up where they were. A step that opens after a click is scrolled into view and given focus.
- **Pick a task.** Each scenario is a radio card with its title and the person's request in Besley italics. The first six are shown and "Show all 30 tasks" opens the rest in place (no box of its own that scrolls, which on a phone is a scroll inside a scroll). "Write the rules" is the one filled button, in a bar that stays at the foot of the screen while the list is longer than it, with which task is picked beside it; while the builder works it says so and how long it takes. Nothing on the page says which tasks are attacks, because seeing whether Chaperone catches one is the point; a test checks the page never says "attack" or "benign".
- **Check the rules.** One sentence on what the rules are for, the request, then every term, one to a row: label, what it says, and a Change button on each term the builder supports editing (category, requirements, brands, price ceiling, quantity, extras, price tolerance). Requirements are read out of the command line's form ("switch_feel = tactile" is shown as "Switch feel: tactile", `requirementsOf`). Change opens a band where the term was, with one text box that starts from the current value, the server's format hint under it (the command line's own `parseEdit` text) and, when the server can't read or accept the edit, its words next to the box, which stays open. "Not covered" says "In your request, but not made a rule", as the run view does. "Lock these rules" is the one filled button (disabled, with the reason, until there is a price ceiling); "Start over" is secondary and the line beside them says what each does. Locked rules stay on screen with the seal and no Change buttons, and step one offers "Pick a different task".
- **Start the run.** The vault. It always says what will happen, as three short lines (the agent shops, the money is held, Chaperone checks and pays, stops or asks), and until the rules are locked that and the held-back button with "Lock the rules in step 2 first." is all it holds. Locked, it asks "How much should Chaperone check?" (Full check, the default; Rules only; Off, which changes the third line to say nobody checks), and states the shopping agent, the money ("Practice money" or "Sandbox", with a line on what that means) and the cost to the person (nothing; a run uses about a cent of the demo's daily budget, with what is left and when it starts again). "Start the run" is the one filled button; it goes to the run view, which follows the run.
- **When live runs can't start** the page says so in an `EmptyState` and what to do instead: "Live runs are off right now." or "Today's live runs are used up." (with the budget and when it starts again), each with "Watch a recorded run" (filled) and "See the benchmark results". The server's own reason for being off (no model key) is an operator's, so it sits behind "Details for whoever runs this server". When the server can't be reached, "Try again". A run already in progress holds the Start button back with an amber note, and the page reads the status again every three seconds until it ends. The refusals of a click (a 409, a 429) are shown in the server's own words by the button that was clicked.
- **On a phone** (390px) nothing scrolls sideways: the terms stack, buttons are full width and at least 44px tall, the tabs wrap, and the SDK example's long lines wrap.
- **Connect your own agent** is documentation only, and says it is for developers, with a link back to the other tab: what the SDK does in three steps, the SDK's own example file in a code block, and three notes (which tools count as payment tools, that v1 protects agents shopping in the arena, and that there is no upload). The code is read from `packages/sdk/examples/protect-your-agent.ts` at build time, so the page, the README and the file are one source; `Start.test.tsx` checks the page shows the file and the README's snippet exactly, beside the SDK's own `test_readme_snippet_is_the_example`.
- **Money, said quietly.** A run that recorded its adapter shows "Practice money" or "Sandbox" as quiet text in the Runs list and in the run view's line under the breadcrumb, always, and a run that didn't (the eval's, the command line's) says nothing.
- **Runs that stopped at the mandate.** A run whose mandate was rejected, couldn't be drafted or hasn't been confirmed has a plain headline ("You rejected the mandate, so no agent ran.", "This mandate is waiting for you.") with a "No run" or "Not confirmed" badge, and isn't followed as if an agent were shopping.
